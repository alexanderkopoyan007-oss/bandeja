# BANDEJA — working notes for Claude

A realistic, fluid 3D padel game for desktop browsers. Free to build, run and host. Full spec: the owner's brief (M0–M8 below); approved plan: `~/.claude/plans/toasty-swimming-bonbon.md`.

## Architecture rules (non-negotiable)
- **`src/sim/` is pure TypeScript**: no DOM, no three, no Node. `tsconfig.sim.json` has `lib: ES2022` and no types, and `tests/sim/purity.test.ts` fails on any forbidden import. Rendering, animation, audio and UI only *read* sim state.
- **Deterministic fixed step at 120 Hz, bit-exact on every machine.** Randomness only from the seeded RNG in `src/sim/core`. Never `Math.random`, `Date.now` or wall-clock time inside the sim. All transcendental maths goes through `smath`, which runs fdlibm ports (`core/fdlibm.ts`): engine `Math.sin/cos/atan/atan2/exp/log/pow` give different last bits on macOS arm64, Linux arm64 and Linux x64 (measured 2026-10-27; the same seed scored 12 points on a Mac and 7 on GitHub's runner). The purity test rejects engine transcendentals in `src/sim`; `tests/sim/smath.test.ts` holds a golden output-bit hash that CI recomputes on Linux. `node tools/det-probe.ts` prints per-function hashes and the sim hash every second, to diff between machines (all four agreed after the fix).
- **Replays = seed + input frames** (`MatchSim.step(input)`). `snapshot()`/`restore()` are not built yet (they come with rollback netcode); `Player.writeState/readState` and `Score.writeState` are the pieces so far. Any new sim state must go in the state hash and in those writers.
- **Input is timestamped** (`event.timeStamp`, `Gamepad.timestamp`, both `performance.now()` time). The sim receives the exact time inside the tick; timing grades use it.
- **Render interpolation** between the previous and current sim state by the accumulator fraction.
- **No allocations in hot loops.** Sim maths writes into preallocated vectors/typed arrays; pools for transient objects. `npm run alloc` runs 100k AI-vs-AI ticks under `--trace-gc`; budget is ≤ 1 minor GC per 10k ticks (~83 s of play), each < 1 ms. Measured 2026-10-27: 10 per 100k, longest 0.17 ms, 1.7 µs per tick.
- **Timing/plan traps** (found the hard way):
  - Contact windows must be searched with the release look-back (`RELEASE_LOOKBACK`, 0.3 s). Searching from "now" makes the ideal of a window you are already in slide forward with the clock: the ring never closes and auto-timing never fires.
  - A re-prediction (after any bounce/wall) restarts the path at the impact: pass `wallsSoFar` and `startFlags` to `Prediction.compute`, or "off the glass" is forgotten and the impact sample looks hittable.
  - Re-planning every few ticks from wherever the player is makes the plan flip between options (player runs back and forth): plans keep their contact unless a clearly better one appears.
  - Anything that changes a shot after `solve()` (e.g. serve spin by key) makes it miss its target: put it in the `ShotRequest` (`spinScale`).
  - The assist must arrive (speed from braking distance), not overshoot: running past the spot puts the body in the ball's line.
- **V8 traps that cause per-tick garbage** (found the hard way):
  - A class field declared without a value (`x: number;`) is emitted as a real field that starts `undefined`; V8 then tags it and boxes every double written to it. Always initialise numeric fields (`x = 0`).
  - `const sqrt = Math.sqrt` aliases are opaque to V8: each call returns a boxed number. `smath` uses tiny wrapper functions instead.
  - Doubles passed into or returned from non-inlined functions get boxed (fdlibm passes its arguments and results through the `IO` Float64Array for this reason). In hot paths pass results through fields (see `Ball.findContact`/`tryWall`, `Player.driveX/driveZ/clock` + `move()`, `SimpleAi.goX/goZ` + `drift()`), read the clock inside (`think(m, f)`, `applyInput(i, f)`), and return sample indices, not times (`bodyHitIdx`). A function that used to be inlined can stop being inlined when its caller grows: the doubles refactor made `think(m, f, t0, t1)` box 4 numbers a tick, and the cloth net grew `Ball.step` until, in about one run in five (JIT timing), `integrate(dt)`/`findContact` (returned a fraction)/`resolve(t)`/`record(t, vn, z)`/`checkExit(t)` stopped being inlined and boxed 24 MB per 100k ticks; they all pass through fields now. Run `npm run alloc` several times: a single good run proves little. `npm run alloc` checks singles and doubles; measured 2026-10-27 with the cloth net: 5-6 and 4 GCs per 100k ticks over six runs.
  - Never reuse `i` for an inner loop inside a method whose parameter `i` is the player number (it sent AI presses to player 0).
  - A tuning field read only on a rare branch has no type feedback there; the first time play reaches it the function deoptimises mid-rally. Read every tuning value a hot function uses up front (`Player.move`, `startLag`).
  - The whole `Ball.step` tree sits near TurboFan's inlining budget: one extra multiply in the bounce made it allocate in about half of all doubles runs, because the wear's `exp()` was inlined into every step. Keep heavy maths out of the bounce (wear is counted there and applied after the step, `Ball.applyWear`), and check `npm run alloc` over 6+ runs after touching ball.ts.
  - smath's `exp()` wrapper is only allocation-free when V8 inlines it; in `Ball.integrate` and `Player.runTime` it sometimes wasn't (one singles run in six, 30 MB per 100k ticks). Hot paths call `FIO[0] = x; expF(); FIO[0]` instead (no double crosses a call). To reproduce a JIT-timing allocation every run, add `--no-concurrent-recompilation` to the child (`node --trace-gc --no-concurrent-recompilation tools/alloc-check.mjs --child 100000 singles`), then `ALLOC_PROFILE=1` with the same flag for the sites.

## Conventions
- Units: metres, seconds, radians, kilograms. Axes: x across the court (left −), y up, z along it; net at z = 0; team 0 on z > 0 (near the broadcast camera).
- Imports inside the project use explicit `.ts` extensions (Node 24 runs sim code directly for tools). Erasable TypeScript only: no `enum`, no namespaces, no parameter properties; use `const` numbers for kinds.
- All tunable content is JSON in `data/` (courts, surfaces, later arenas, rackets, players). Code reads it; don't hard-code numbers that belong in data.
- Exact-pinned dependencies. three 0.186.1 (`three/webgpu`, TSL), vite 8, vitest 5, typescript 7.
- The Browser pane cannot capture a WebGPU canvas (it shows black). For visual checks use `node tools/shot.mjs <url> <png>` (real Chrome, WebGPU) or `?backend=webgl` in the pane.

## Court interpretation (FIP Rules of Padel, application 01.01.2026)
- 20 × 10 m inside; net 0.88 m centre / 0.92 m posts, posts ≤ 1.05 m; service lines 6.95 m from the net; centre line extends 20 cm past them; lines 5 cm.
- Back walls: 3 m wall + 1 m mesh. Side walls, variant 1 (standard): 3 m × 2 m then 2 m × 2 m glass steps; enclosure 4 m high over the 4 m stepped section, 3 m in the centre. Variant 2 (panoramic): 3 m × 4 m glass, mesh to 4 m over the extreme 2 m only. The PDF's "3 m in the center 6 meters" wording is ambiguous; this is our reading.
- Two openings per side flank the net post with a divider post (rule 13.b); 1.05–1.10 m wide, 2.0–2.2 m high.
- Narrow singles (20 × 6 m) is not an FIP court; it is our variant.
- Ball: 6.35–6.77 cm, 56.0–59.4 g; dropped from 2.54 m must bounce 135–145 cm (altitude ball above 1000 m: 122–135 cm). This is the bounce model's calibration test.
- Scoring options per the PDF: Advantage, Star Point, Golden Point (no default named; ours is Star Point). Serve and point rules: see `src/sim/rules` and their tests, which cite rule numbers.

## Tools
- **One headless Chrome at a time on this machine.** Run every Chrome-launching tool through `bash tools/one-chrome.sh <cmd>` (shares the lock/queue with the Meridian project's audit tools, which run in parallel sessions). Never `pkill` Chrome by pattern: other sessions' puppeteer Chromes look identical; stop only PIDs you started.
- `bash tools/one-chrome.sh node tools/shot.mjs <url> <png> [waitMs] [w] [h]`: real-Chrome screenshot (the Browser pane shows WebGPU canvases as black).
- `npm run alloc`: GC budget check for the sim, and for the four animated bodies (`avatars` mode; `ALLOC_PROFILE=1` lists allocation sites, garbage included; `ALLOC_SEED=` another match: GC counts vary with match content, so compare a few seeds before blaming a change). `npm run perf`: frame-time report (needs `npm run build`; it takes the one-Chrome lock itself, so never wrap it in `one-chrome.sh` again: the inner call would wait on the outer's lock, and every other session's Chrome with it).
- `node tools/ball-lab.ts [tag]`: the ball lab (`src/sim/lab/ballLab.ts`): 38 shots at the floor, glass, mesh, corners and joins, measured per contact; writes `docs/lab/ball-lab-<tag>.md/.json`. `?lab=ball[&shot=id]` replays them on the court in the browser (orbit with the mouse, arrow keys step through). `tests/sim/ballLab.test.ts` holds the tuned numbers.
- `node tools/point-mix.ts [seeds] [secs] [singles]`: how AI-vs-AI points end (reasons, the shot and timing grade behind errors, rally length). For tuning the AI's error mix.
- `npm run assets`: rebuild `public/assets/player.bnz` from `assets-src/mixamo/` (raw Mixamo, only on the owner's machine). Commit the .bnz, never the FBX.
- Browser-pane captures when the Chrome queue is busy: the page exposes `window.__bandeja` before its warm-up, so a script can stop the loop, step `g.tick()` itself (`g.epoch -= 1000/60` per frame), `renderer.setSize(1280, 720, false)`, render and `canvas.toBlob` to a localhost receiver. Call `skeleton.update()` on each avatar mesh before a manual render: three refreshes skin matrices once per animation-loop frame, so manual renders otherwise show the racket off the hand.
- `bash tools/one-chrome.sh node tools/bot-play.mjs [url] [secs]`: plays as the human (player 0) with real keyboard events timed in the page, releasing on `focusIdeal` (the ring's moment); in doubles it plays only the balls given to it. Checks that grades use exact key timestamps (p50 error ≈ 8 ms while frames are 33 ms).
- URL options: `?mode=singles` (default doubles) `&styles=muro,martillo,serpiente,reloj` (AI style by player number) `&lefty=0,3` (left-handers by player number) `&autoplay=1 &seed= &court=standard|panoramic|singles-narrow &floor=turf|hard|carpet|clay &scoring=star|golden|advantage &ai=0..1 &assist=0..1 (default 0.45; 0 = keys always move, no aim target) &timing=1..2 (window scale, default 1.5; 1 = strict) &autotime=1 (a held swing fires itself, graded Good) &pro=1 &aim=mouse &alt= &temp= &windx= &windz= &backend=webgl &dpr= &arena=stadium|hall|club-day|club-night &photo=<id> (photo-match; &lines=1, &still=1) &gfx=tv (broadcast graphics) &bloom=0 &tone=agx|aces`.
- Captures from a hidden Browser-pane tab (no animation frames there): `await window.__step(secs)` steps the game, `await window.__snap(name, kind, at, w)` renders one frame (or a photo-match composite) and posts it to a receiver on 127.0.0.1:5198. Use `?backend=webgl`. Any post-processing must skip a 0 x 0 canvas (targets made at zero size stay black in WebGL).

  - Racket–ball impact (2026-10-27, `src/sim/contact/racket.ts`, `data/rackets.json`, `tests/sim/racket.test.ts`):
    - The racket is a free rigid body (mass, balance, I across the face, I about the handle). Apparent COR at a contact point is ea = (e − r)/(1 + r) with r = (m/M)(1 + M b²/I_cm + M x²/I_polar), e falling with impact speed. Fitted to Viollaz's padel ACOR surfaces: 0.50 at 17 m/s and 0.39 at 29 m/s at the best point; curvature −1e-5/mm² along the face, −4e-5/mm² across. Smash point (83 mm from the tip) < drive (128) < volley (146).
    - Forward impact (`impact`): normal impulse m(1+ea)u, then friction: the ball grips (contact-point slip reversed by tangentialE) when μ·Jn allows it, else slides; spin from the friction impulse. An off-centre hit twists or rocks the face during the dwell and turns the ball off line.
    - Inverse (`swing`): the face normal and face velocity that send the ball out with the wanted velocity and spin, within the friction cone, at the swing's average contact (`meanAcor`, so a scattered contact point doesn't lower every shot), refined 4 times through the forward model.
    - `ShotSolver.strike`: each shape caps the racket face speed (`racketMax`, at its `impact` point from the tip), not the ball speed. A hard incoming ball comes back faster off the same swing (a blocked smash). When the face can't give both: spin goes first (down to `spinFloor`), then pace; if the face still can't give the spin, the flight is re-solved with the spin it does give. Errors are made in the swing (`shots.json` `swing`: path yaw/pitch, face open/yaw, speed, contact along/across the face, timing turning the path) and pushed through the impact; contact past the face's edge is a frame shot.
    - Measured (12 seeds × 300 s doubles AI): smash median ≈ 138 km/h (Rivilla-García 2019: semi-pros 133 unopposed); points 194 (was 168), own-side errors 50.5%, double bounce 40.7%; slice errors 4%, chiquita 5.5%.
    - Traps: spin costs face speed, so a slice or chiquita that keeps its spin at a capped face speed falls short into the net (hence spin-first reduction and the re-solve); the solver's fallback must loop a short ball over the net, not let it fall short; the twist across the face dominates the scatter (contact across is the tight spread); the old chiquita test passed only because the drive climbed the back glass (it now checks height at the net players).
